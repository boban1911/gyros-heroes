# Loyalty Card Feature — Implementation Plan

## Context

Gyros Heroes wants to introduce a digital-only loyalty program: customers register on the website, receive a Google Wallet pass (no physical card), and staff scan the pass's QR at the counter to add stamps. The first mechanic is "buy 9, get the 10th free," but the rule must be configurable. The codebase today is a pure Vite SPA deployed on Vercel with no backend, no auth, and no database (Supabase env vars exist but are unused). This plan adds a thin backend on Vercel Functions, a Neon Postgres database with branch-per-environment, a customer registration flow, a Google Wallet integration with a rotating-barcode anti-abuse design, and a separate staff scan PWA.

Decisions confirmed with the user:
- Staff use **per-employee accounts** (audit trail, individual revocation).
- DB: **Neon Postgres** with **Drizzle ORM** + drizzle-kit migrations.
- Scan app: **separate Vite entry** (`scan/index.html`) — its own bundle, manifest, and service worker; mirrors the existing `pozivnica/` multi-HTML pattern in `vite.config.ts:51-57`.
- Loyalty config: **DB row + admin page**, so rule changes don't require deploys.
- Wallet: **Google Wallet first**; Apple Wallet deferred.
- Auth: **email magic link** for customers (double opt-in serves as email verification + GDPR consent).

## Schema (Drizzle, in `db/schema.ts`)

```ts
customers          (id uuid pk, email citext unique, name text, email_verified_at timestamptz, created_at timestamptz)
magic_links        (token_hash text pk, customer_id uuid fk, expires_at timestamptz, used_at timestamptz)
loyalty_cards      (id uuid pk, customer_id uuid fk unique, stamps_count int default 0,
                    total_redemptions int default 0, status text check in ('active','ready_to_redeem'),
                    google_object_id text unique, created_at timestamptz)
stamp_events       (id uuid pk, card_id uuid fk, type text check in ('stamp','redeem'),
                    staff_id uuid fk, qr_jti text, created_at timestamptz)
qr_tokens          (jti text pk, card_id uuid fk, issued_at timestamptz, expires_at timestamptz, used_at timestamptz)
                   -- prevents replay; we mark used_at on first scan
staff_users        (id uuid pk, email citext unique, name text, password_hash text,
                    role text check in ('staff','admin'), is_active boolean, created_at timestamptz)
staff_sessions     (token_hash text pk, staff_id uuid fk, expires_at timestamptz)
loyalty_config     (id int pk default 1, stamps_required int default 10,
                    reward_description text, scan_cooldown_seconds int default 1800,
                    qr_token_ttl_seconds int default 60, updated_at timestamptz)
```

Singleton row in `loyalty_config` enforced by `id = 1` PK.

## Anti-abuse: rotating QR

Static QR codes in wallet passes are trivially screenshot-shareable. Design:

1. The Google Wallet pass object's barcode `value` is **not the customer ID**. It's a short JWT signed by our server: `{ cardId, jti, iat, exp }` with `exp = iat + qr_token_ttl_seconds` (default 60s).
2. Google Wallet supports periodic barcode refresh via the **rotating barcode** feature on `LoyaltyObject` — we configure `rotatingBarcode.totpDetails` so the Wallet app generates time-based codes locally from a shared secret, OR (simpler) we push pass updates from the server every N seconds via Wallet REST API. **We'll use server-pushed updates** triggered by a cron-style Vercel scheduled function every 30s for active cards, plus an immediate refresh when the customer opens the pass detail page.
3. On scan, `api/staff/scan.ts` validates: signature, `exp > now`, `jti` not in `qr_tokens.used_at`, marks `used_at = now`, applies cooldown (`scan_cooldown_seconds` since last stamp on this card), then increments `stamps_count` and writes a `stamp_events` row.
4. If `stamps_count == stamps_required`, set `status = 'ready_to_redeem'` and update the wallet pass visual (different background / "FREE GYROS!" text) via Wallet REST API.
5. On redeem (separate staff button), reset to `stamps_count = 0`, `status = 'active'`, increment `total_redemptions`, push pass update.

## Routing & UI flows

**Customer registration**
1. `/loyalty` — form: name + email + GDPR checkbox. POST `/api/auth/register`.
2. Email arrives via Resend with link `https://gyrosheroes.rs/loyalty/verify?token=…` (token = HS256 JWT, 24h TTL).
3. `/loyalty/verify` — calls `/api/auth/verify`, sets `gh_session` HTTP-only cookie, creates `loyalty_cards` row + Google Wallet object, renders **"Add to Google Wallet"** button (uses signed Save-JWT from `/api/wallet/google/save-jwt`). Same email also includes the Save link as a backup.
4. `/loyalty/card` — view-only state (stamps progress, redemption status). Re-shows wallet button if not yet added.

**Staff scan**
1. `/scan/login` — email + password → `/api/staff/login` → `gh_staff` cookie.
2. `/scan` — full-screen camera (`html5-qrcode` with `BarcodeDetector` fast-path). On detect, POST `/api/staff/scan` → toast: "Marko +1 → 4/10" or "🎉 REDEEM FREE GYROS — confirm?" with a confirm button that calls `/api/staff/redeem`.
3. PWA installable: manifest scope `/scan/`, standalone display, Gyros Heroes icon.

**Admin**
1. `/admin` (gated by `staff_users.role = 'admin'`): edit `loyalty_config`, add/disable staff users, view recent `stamp_events`.

## Neon branching strategy

- Install the official **Neon ↔ Vercel integration** from the Vercel Marketplace. This provisions:
  - `DATABASE_URL` for production → Neon `main` branch.
  - `DATABASE_URL` for preview deployments → ephemeral branch per Vercel preview, auto-cleaned on PR close.
  - `DATABASE_URL` for development → long-lived `dev` branch for local `npm run dev`.
- Local `.env.local` gets the `dev` branch URL via `vercel env pull`.
- Migrations: `drizzle-kit push` against the relevant branch. Add `npm run db:generate`, `npm run db:migrate` scripts. Production migrations run via a one-shot Vercel build step (`drizzle-kit migrate` in the build command, gated by `VERCEL_ENV === 'production'`) or manually via CLI for early stages — start with manual to keep blast radius small.

## Environment variables (Vercel)

Public (`VITE_` prefix, exposed to client):
- `VITE_GA_MEASUREMENT_ID` (existing)
- `VITE_GOOGLE_WALLET_ISSUER_ID` (only the public issuer ID, used to build Save URLs)

Server-only (Vercel Functions):
- `DATABASE_URL` (managed by Neon integration)
- `JWT_SECRET` (random 32+ bytes, signs magic-link / QR / session tokens)
- `RESEND_API_KEY`
- `RESEND_FROM_EMAIL` (e.g., `noreply@gyrosheroes.rs`)
- `GOOGLE_WALLET_SERVICE_ACCOUNT_JSON` (base64-encoded service-account key)
- `GOOGLE_WALLET_ISSUER_ID`
- `GOOGLE_WALLET_CLASS_ID` (set after one-time class creation)
- `APP_BASE_URL` (e.g., `https://gyrosheroes.rs`) — used in email links

## Implementation order (suggested)

1. **Infra scaffold (no UI yet)** — install Neon-Vercel integration, add `DATABASE_URL`, install Drizzle, create `db/schema.ts` and first migration, deploy to confirm functions run on Vercel.
2. **Auth + registration** — `api/auth/register`, `api/auth/verify`, Resend email, `/loyalty` and `/loyalty/verify` pages. End-to-end magic-link flow with cookie session, no wallet yet.
3. **Google Wallet pass** — one-time loyalty class creation script (committed under `scripts/create-wallet-class.ts`), `api/wallet/google/save-jwt.ts`, "Add to Google Wallet" button on `/loyalty/verify`. Static barcode initially (cardId), to validate the path.
4. **Staff PWA + scan endpoint** — new Vite entry, login + scanner UI, `api/staff/scan.ts` with naive validation. Manually create first staff user in DB.
5. **Rotating QR + replay protection** — switch barcode to short-lived JWT, add `qr_tokens` table, server-push pass updates, rate-limit cooldown.
6. **Redemption flow + status visual change** — `api/staff/redeem.ts`, pass background/title swap when ready.
7. **Admin page** — `/admin` for `loyalty_config` editing and staff management.
8. **GDPR polish** — privacy-policy update, `api/account/delete.ts`, "delete my account" link in `/loyalty/card`.

Each step is independently deployable and testable.

## Verification

End-to-end smoke test once steps 1–4 ship:

1. **Register**: open `/loyalty`, submit name + email, confirm magic-link email arrives (check Resend dashboard in dev).
2. **Verify**: click link → land on `/loyalty/verify`, see "Add to Google Wallet" button, click → pass appears in Google Wallet on phone.
3. **Scan as staff**: open `/scan/login` on a separate device, log in with seeded staff account, point camera at the wallet pass barcode → toast shows "+1 → 1/10". Refresh `/loyalty/card` → counter is 1.
4. **Replay defense (after step 5)**: screenshot the wallet barcode, attempt to scan the screenshot 5 minutes later → server rejects (`exp` past). Scan a fresh QR twice within cooldown → second rejected.
5. **Redeem**: stamp 9 more times (use a dev-only seeder or just scan repeatedly with cooldown disabled in `dev` config) → after 10th, pass visual switches to "FREE GYROS!". Press redeem → counter resets to 0 and `total_redemptions` increments.
6. **Admin** (after step 7): change `stamps_required` to 5, register a new test customer, confirm reward triggers at 5.

Automated tests:
- Vitest unit tests for `lib/jwt.ts`, `lib/wallet/google.ts` (mocking the Google client), and the rate-limit helper.
- Component tests for the `/loyalty` form (validation, submit states) and the `/scan` scanner result toast — follow patterns in `tests/components/`.
- Integration test mocking the Neon driver to verify scan endpoint state transitions.
- Existing `tests/verify-assets.test.ts` and `tests/tailwind-theme.test.ts` must keep passing.

Manual checks:
- `npm run build` — type-check + Vite build succeeds with both entries.
- `npm run preview` — serve, confirm `/scan/` is reachable as its own bundle.
- Lighthouse on `/scan/` — confirm PWA installability score.

## Out of scope (v1)

- Apple Wallet — separate later track once the Google flow is validated.
- Multi-store reporting — schema supports a `store_id` later, but v1 is single pool per user request.
- Offline scanning in the staff PWA — requires conflict resolution; defer.
- Push notifications to wallet pass on stamp updates beyond the standard Google Wallet update.
- SMS/phone auth.

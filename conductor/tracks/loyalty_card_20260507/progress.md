## Open questions / decisions to revisit

- **Rotating-barcode mechanism — RESOLVED.** Both web (option a, JWT live QR) and wallet pass (option b, `rotatingBarcode.totpDetails`) shipped. The scanner accepts both formats by prefix dispatch. Option (3) server-pushed updates was deemed unnecessary and not implemented.
- **Existing wallet passes still embed the old static barcode.** `ensureCustomerWalletObject` short-circuits when `googleObjectId` is already set, so customers who saved the pass before Step 5 landed will keep showing the static `gh:card:<uuid>` until they re-save (or until a one-shot sweep patches them). Decide later whether to write a one-time `patchLoyaltyObject` migration script or notify users to re-save. Same applies to the new `rotatingBarcode` block — old passes won't pick it up automatically.
- Whether to keep "login.ts" / "logout.ts" alongside magic-link verify, or fold them in (commit `37970a2` mentions register/login email split). Still open.
- Loyalty model: confirmed with user that block-at-threshold (current behavior — no over-stamping past 10) matches typical paper punch-card UX. Stockpiling rewards (`pending_rewards` counter) is *not* a v1 requirement.
- Pass title text — only `hexBackgroundColor` and `textModulesData` change on threshold; the program-level title ("Hero kartica") stays put. If you want the headline itself to read "FREE GYROS!" we'd need to patch a class-level field or use `localizedHeader` on the object.
- Brand hex values are duplicated between `lib/wallet/loyaltyClass.ts` and `lib/wallet/passVisual.ts`. If they ever drift, the active-state revert will look wrong. Consider extracting a shared `lib/wallet/colors.ts` later.
